# Marque 4.3 — 2026-09-02

## What changed

`marque/usarrs` now registers routes for **email verification** and **password
confirmation**. If you're not using either feature, this changes nothing for you —
but if your app (or usarrs' own admin panel) uses Laravel's standard `verified` or
`password.confirm` middleware, this fixes a real bug: those routes were silently
missing, which meant anyone who wasn't already verified had no way to ever become
verified.

## Why

Marque 4.2 made `marque/usarrs` require `laravel/fortify` and suppress Fortify's own
routes unconditionally — the right fix for a route-collision security issue (see
[Marque 4.2](4.2.md)). But that release only re-registered *some* of Fortify's route
groups (login, register, password reset, two-factor) under usarrs' own name. Two were
missed: email verification and password confirmation.

The consequence: with Fortify's routes gone and nothing replacing these two, there was
no route anywhere that could satisfy Laravel's built-in `verified` middleware or
`password.confirm` middleware. Not a security hole — the opposite. A **lockout**: any
unverified user hitting a `verified`-gated route had nowhere to go, permanently.

This was found by a deliberate cold-upgrade test — someone upgrading a real app from
an old version, on purpose, without shortcuts — rather than by anything failing
loudly. It's also the kind of thing usarrs' own shipped defaults were quietly relying
on: usarrs' admin panel config defaults to requiring `verified`, so the bug affected
usarrs' own admin panel out of the box, not just a hypothetical downstream use case.

## Who's affected

Only sites using **`marque/usarrs`** who use Laravel's `verified` or
`password.confirm` middleware anywhere — including usarrs' own admin panel, which
uses `verified` by default. If you've never touched either middleware and don't use
the admin panel, this doesn't affect you functionally, though you should still
upgrade for the fix.

**One thing to check on your `User` model:** email verification only works if your
model does `implements \Illuminate\Contracts\Auth\MustVerifyEmail` — not just uses
the trait of the same name. This is a well-known Laravel gotcha (the base
`Illuminate\Foundation\Auth\User` class has the same gap), not something this release
introduced, but it's worth checking now if you plan to rely on email verification for
the first time.

## What you need to do

**If you don't use `verified` or `password.confirm` middleware:** just upgrade.
Nothing else changes.

```bash
composer require marque/usarrs:^6.1
```

**If you do use either middleware** (or the admin panel), also confirm your `User`
model has:

```php
class User extends Authenticatable implements MustVerifyEmail
{
    use \Illuminate\Auth\MustVerifyEmail;
    // ...
}
```

If it's missing, the `verified` middleware will have been silently doing nothing —
adding this now makes it actually enforce, which is a behaviour change worth testing
before it reaches production.

No database migration, no config change, no other action needed.

## Packages affected

- `marque/usarrs` — v6.0.0 → v6.1.0

Nothing else in the suite changed in this release.
