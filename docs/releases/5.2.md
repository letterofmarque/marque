# Marque 5.2 — 2026-09-09

## What's new

- **`marque/taxonomy`** (new package) — lets a tracker declare how its
  catalogue is organised in a YAML file, instead of that shape being baked
  into the database. Categories, hierarchies and filters become something
  you write, not something you fork the code to change.

Optional. Nothing else requires it, and if you don't install it your
`torrents` table gains no taxonomy columns at all.

## The problem it solves

Most tracker software makes your subject matter a schema decision. Gazelle
carries `media`, `format`, `encoding`, `remaster_year` as columns on
`torrents` — a music-shaped tracker wearing a config file. Run something
else at it and each new kind of content means schema changes, a rewritten
upload form and a rewritten search builder.

There's a subtler version of the same trap that anyone who has run a real
tracker will recognise. A free-form category tree lets the same idea sit at
different depths in different branches — one league needs a division level,
another doesn't — and once that happens, "show me every week 12 game"
becomes unanswerable, because the tree has no idea those nodes are the same
kind of thing. The flat-list alternative fails the other way: a `parent`
column nobody uses, and the season baked into every category name
(`NFL 2013`, `NFL 2014`, …), one row per season, added by hand, forever.

With taxonomy, levels are **typed dimensions scoped to a content type**
rather than nodes at some depth. So these are single queries, and they reach
across every domain that declares the level:

```php
$query->where('season', '2006')->get();   // every league's 2006
$query->where('week', '12')->get();       // every season's week 12
```

## What a definition looks like

One file in `config/taxonomies/`:

```yaml
content_type: nfl_game
label: NFL Game
version: 1

levels:
  - season: { label: Season, type: year }
  - week:   { label: Week, type: integer, range: [1, 22] }

facets: [resolution, source, codec, subtitles]
```

That's complete and working — no migration, no deploy, no PHP. A second kind
of content is a second file, with a different shape:

```yaml
content_type: cricket_match
label: Cricket Match
version: 1

levels:
  - season:  { label: Season, type: year }
  - format:  { label: Format, type: string }
  - innings: { label: Innings, type: integer, range: [1, 4] }

facets: [resolution, source, subtitles]
```

Both declare `season` and they don't collide — levels belong to their
content type. A cricket uploader never sees `Week`, and each type's ranges
apply only to its own levels.

## What it gives you

- **A cascading upload form.** Pick the kind of thing, then walk the
  hierarchy one step at a time, each dropdown filled from the previous
  choice.
- **An admin screen** for populating the values you actually run — which
  leagues, which seasons, which resolutions. It deliberately offers no way
  to add or remove a *level*: those come from the definition, which is what
  stops a catalogue drifting into the mess described above.
- **Filtering across the hierarchy**, not just down it.
- **Many-valued facets** — a modern rip with a dozen subtitle tracks
  classifies without loss, and filtering on any one of them finds it.
- **Protection from your own edits.** Removing a level or dropping a facet
  never happens silently: a command reports exactly what it will orphan and
  asks first. Classification data is never deleted — rows become
  unreferenced and recoverable.
- **Safe package updates.** A definition that changes shape must declare how
  to migrate, or the loader refuses it. `composer update` cannot reshape a
  live catalogue behind your back.

## Who's affected

**Nobody, unless you want it.** This is a new optional package. No existing
package changed, no schema you already have was touched, and no upgrade is
required to stay where you are.

It's most useful if you run a tracker where "what kind of thing is this"
has more structure than a flat category list — sport, TV, film, anything
with seasons, series, events or stages.

## What you need to do

Nothing, to stay put. To try it:

```bash
composer require marque/taxonomy
php artisan migrate
```

Then write a definition in `config/taxonomies/`, and check it:

```bash
php artisan marque:taxonomy:validate
```

That command exits non-zero on a bad file, so it works as a deploy gate. A
definition that doesn't validate is refused whole — the tracker keeps
running on whatever it had before, rather than half-applying a new shape.

Full documentation, including the complete YAML reference and the migration
format, is in the [package README](https://github.com/letterofmarque/taxonomy).

## Domain packages

The engine ships **no vocabulary of its own** — it doesn't know what a
season, a series or an episode is, and a test enforces that. Definitions
come from you, or from a domain package.

The convention for those is `marque/taxonomy-sport`, `marque/taxonomy-tv`,
`marque/taxonomy-film` — so someone wanting a film tracker can find one.
None of those exist yet; the engine landed first deliberately, so its
domain-neutrality could be proven before anything depended on it.

If you write your own, a definition in your app's `config/taxonomies/`
always overrides a package-shipped one of the same name, and a package
update will never silently replace your version — though it will tell you a
newer one exists.
